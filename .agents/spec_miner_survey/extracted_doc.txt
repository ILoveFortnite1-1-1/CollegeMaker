1. Product intent
Goal. Give any student a focused workspace to discover colleges, compare them, understand fit/tradeoffs, estimate costs, review outcomes, and save a personalized list without requiring an account.
Core experience
Dashboard-first: a student sees their saved colleges, high-level portfolio signals, and the next decision to make.
College profile: each institution has a consistent, scannable structure regardless of school type or size.
Compare: students can place multiple colleges side-by-side using the same normalized fields.
Explain, do not decide: fit scores and recommendations are transparent and adjustable rather than absolute.
Freshness by design: new or missing college data can be enriched on demand by a server-side model call, with every pulled fact added to the shared master knowledge document.

8. Server-side AI college lookup
Provider abstraction. The application should call your server, never the model vendor directly from the browser. Your server can route the enrichment request to a model such as a Gemini Flash-class model, another provider, or a later replacement without changing the frontend contract.
8.1 Flow
1.  Student searches for a college or opens an unknown institution.
2.  Server checks the structured College record and freshness rules.
3.  If data is missing/stale, server creates an EnrichmentRun and calls the configured model provider.
4.  Model returns structured JSON only: identity, fields, values, sources, confidence, notes, and unknowns.
5.  Server validates the response against a schema; reject or quarantine malformed/unsupported data.
6.  Server writes normalized metrics + evidence rows to the database.
7.  Server appends every newly pulled or changed fact to the master knowledge document with provenance.
8.  Client receives the normalized college profile plus freshness state and refresh timestamp.

10. Freshness, provenance, and trust
Requirement
Behavior
Source on every fact
Each metric stores at least one source ID; derived scores store the input fact IDs and calculation version.
Freshness
Show Last refreshed on profiles; define configurable TTLs by field group. Admissions and cost data can expire faster than static identity data.
Confidence
Model-supplied confidence is advisory; server validation and source quality rules can lower or raise the final confidence band.
Conflicts
Do not merge conflicting values silently. Store both evidence records and mark the field “needs review” until a deterministic rule resolves it.
Model versioning
Persist provider, model, prompt version, schema version, and run ID for every enrichment.
Auditability
A staff/admin view can trace a profile field back to the enrichment run and source evidence that created it.

12. Compare experience
Allow 2–6 colleges in a comparison set.
Keep row definitions identical across institutions; do not mix “reported” and “estimated” without status labels.

Allow a student to pin rows, hide low-value rows, and export the current comparison.

14. Security and privacy boundaries
The model API key and provider credentials exist only on the server.
The browser never sends arbitrary prompts directly to the model vendor.
Treat model output as untrusted input; validate against a strict schema and sanitize rendered text/URLs.
Rate-limit enrichment endpoints and cache repeated college lookups.
Store the smallest amount of student data needed for portfolio behavior; keep analytics optional and separate from essential save functionality.
Provide deletion of saved portfolio data and the associated cookie identifier.
15. Prompt-injection resistance for college research
Because external college pages and search results are untrusted inputs, the enrichment pipeline must explicitly defend against instructions embedded in retrieved content. Treat every page excerpt as data, not as instructions to the model.
Control
Implementation
System policy
The enrichment agent is told that retrieved web text is untrusted evidence and can never override its task or system rules.
Structured extraction
Ask for schema-constrained JSON rather than free-form narratives.
Source isolation
Place source text in clearly delimited evidence fields; do not concatenate it into control instructions.
Tool permissions
Model can request lookup data, but cannot directly write production records. Server validates and commits changes.
Review queue
Flag suspicious, contradictory, or unusually broad outputs for manual review.

17. Acceptance criteria
A new student can open the app and save a college without creating an account.
Saved colleges persist across reloads via a first-party portfolio cookie linked to server-side data.
A college profile uses the same generic modules regardless of institution.
A user can compare at least two colleges using identical normalized fields.
A missing/stale college can be enriched through a server endpoint without exposing provider credentials to the browser.
Every enrichment creates an auditable run record with provider/model, prompt version, timestamp, and result status.
Every new or changed fact from enrichment is appended to the master knowledge document with provenance.
Malformed or contradictory model output cannot silently overwrite trusted structured data.
The UI clearly labels reported, estimated, projected, and qualitative information.
The dashboard and profile remain usable on mobile widths and with keyboard navigation.
18. Suggested implementation sequence
1.  Foundation: routes, design tokens, reusable cards/tables, College + Portfolio data model.
2.  Portfolio: cookie-backed anonymous ID, save/remove college, dashboard list.
3.  Profiles: generic college profile + source/freshness labels.
4.  Compare: normalized comparison table and adjustable fit weights.
5.  Enrichment: server adapter, strict schema, validation, caching, async jobs.

Design conclusion. Keep the student-facing experience simple and visual, keep the data layer strongly structured, and treat AI enrichment as a controlled ingestion pipeline whose output is both usable in the app and permanently auditable in the general knowledge document.
Programmatic College Data & AI Enrichment
A large portion of college information should be collected programmatically from structured, authoritative sources. The application should use AI as an enrichment and synthesis layer rather than as the primary source of truth.
Recommended Data Sources
U.S. Department of Education College Scorecard: Use for admissions, enrollment, completion, costs, financial aid, earnings, majors, and institution metadata.
IPEDS / NCES: Use for detailed institutional statistics including enrollment, tuition, degrees, demographics, staffing, and graduation information.
Official college websites and Common Data Set documents: Use for fields that are unavailable or inconsistent in federal datasets, especially current admissions, academics, programs, and institutional details.
Server-side Gemini endpoint: Use for missing or qualitative information, source synthesis, classification, summaries, and extracting structured information from permitted sources.
College Lookup Flow
1. Check the master college database first.
2. If the record exists and its data is sufficiently recent, return the stored record.
3. Query College Scorecard and/or IPEDS for authoritative structured fields.
4. Normalize external responses into the application's canonical college schema.
5. Identify missing, stale, or qualitative fields.
6. If necessary, call the server-side Gemini endpoint for only those remaining fields.
7. Require structured JSON from the AI response, including source information and retrieval dates where applicable.
8. Validate the response before accepting it.
9. Merge accepted information into the master college record.
10. Return the normalized college object to the frontend.
Canonical College Record
The master data store should use a structured record rather than relying on a free-form document as the database. Example:
{  "id": "college-slug",  "name": "Example University",  "location": {    "city": "Example City",    "state": "EX"  },  "admissions": {    "acceptance_rate": {      "value": 0.31,      "source": "college_scorecard",      "retrieved_at": "2026-09-02"    }  },  "cost": {    "tuition_in_state": {},    "tuition_out_of_state": {},    "average_net_price": {}  },  "outcomes": {    "graduation_rate": {},    "median_earnings": {}  },  "academics": {},  "student_life": {},  "qualitative": {    "career_strengths": [],    "campus_notes": []  }}
Shared Master Knowledge Layer
When a lookup discovers new information, the accepted information should be written to the shared master college record. This means a lookup performed for one student can benefit later students without requiring another AI call.
Keep the canonical structured database as the source of truth. A generated Markdown document or JSONL export can also be maintained for portability, search, auditing, or retrieval-augmented generation.
Data Provenance and Trust
Every non-trivial field should retain provenance. At minimum, store the value, source, retrieval/update date, and data classification.
Reported — directly supplied by a trusted source.
Calculated — derived from reported values using a deterministic formula.
AI-derived — extracted, classified, or summarized by the AI service.
Estimated — an explicit estimate rather than an observed value.
Source Precedence
Do not allow an AI response to silently overwrite higher-confidence data. Use a source hierarchy:
Official government or structured institutional data.
Official institution documents and websites.
Other reputable primary or secondary sources.
AI-extracted or AI-summarized information.
Model estimates.
Server API Architecture
A simple server-side architecture can expose endpoints such as:
GET  /api/colleges/:collegeIdPOST /api/colleges/:collegeId/refreshGET  /api/portfolioPOST /api/portfolio/colleges/:collegeIdDELETE /api/portfolio/colleges/:collegeIdPOST /api/ai/college-enrichment
The frontend should never need direct access to the Gemini API key. The server calls the configured model endpoint, validates the response, applies source precedence, updates the master record, and then returns safe normalized data to the browser.
Cookie-Based Saved Colleges
Use a small browser cookie only as an anonymous portfolio identifier. Store the actual saved college IDs server-side rather than placing full college records in cookies.
Cookie:student_portfolio_id=<random-opaque-id>Server-side portfolio:{  "portfolio_id": "<random-opaque-id>",  "saved_colleges": [    "college-a",    "college-b",    "college-c"  ]}
Recommended Request Flow
Browser → Your Server → Master College DB → Scorecard/IPEDS/official sources → Gemini only for remaining gaps → validation → master DB update → normalized response → Browser
This design keeps the UI fast, reduces duplicate AI requests, preserves source provenance, and creates a continuously improving shared college knowledge base.
